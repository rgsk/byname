**What the port settled on** (shapes for torch code in `.pyn`):
- **Configs are records** with `type GPTConfig = (...)` aliases (closed: exact fields) at the top. Functions take them as named parameters with inline open types, destructured in the body: `def __init__(self, cfg: (..., vocab_size: int, …)):` then `(vocab_size=, …) = cfg`, called as `GPT(gpt_cfg)`.
- **Defaults hold only size-independent fields** (`train_defaults = (eval_interval=100, eval_iters=100)`); each config spreads them and must set the size-dependent ones: `train_cfg: TrainConfig = (**train_defaults, batch_size=32, ...)`. `_replace` from a full config was rejected: a stale `block_size` rides along silently. The annotation is what checks a config against its closed type; an unannotated spread of known names is still typed (see Spreads).
- **`nn.Module.__call__` is `Callable[..., Any]`,** so `model(x)` is `Any`. `GPT` gets a checker-only `if TYPE_CHECKING: def __call__(self, idx: Tensor) -> Tensor: ...` (`__call__ = forward` doesn't work: the base's declared type wins). Calls to torch's own layers inside `forward` get one annotation at the first local (`qkv: Tensor = self.qkv(x)`); einops' `rearrange` is generic, so types flow through it.

## Measured facts (don't re-measure)

- **Return-type inference through the translation:** pyright, basedpyright and Pyrefly give identical results (`-> _rec_…[str, int]`, field types, and an error on unknown fields). ty returns `Unknown` everywhere.
- **Checkers (2026-10-05): basedpyright (and pyright) is the only supported checker;** byname is designed and tested against it. Every other checker (mypy, Pyrefly, ty) is not supported: no workarounds, no tests, no docs. mypy was also dropped from `byname tool`'s docs and the dev dependencies, and its workarounds were removed from the translation (2026-10-05: the `if MYPY:` branch, the `Any` default on `_byname_ctx`'s TypeVar, `# type: ignore` comments; basedpyright's output on every `.pyn` in the repo was unchanged). The proxy can still run another checker (`byname.checker`), unsupported. Measured on 2026-10-04, kept for reference: a 29-case matrix of every feature, each line tagged as an expected error or not:
  - basedpyright 1.40.1: all right.
  - Pyrefly 1.3.2: misses errors in all 4 spread-built records (`p: T = (**u,)`, `f((**u,))`, `f(p=…)`, overloads), never a false error: it doesn't give a lambda's parameter the expected type, so they're unchecked. Everything else matches basedpyright.
- **basedpyright's default mode is noisy:** "recommended" flags `reportImplicitRelativeImport` and similar. `byname tool` uses `standard`, unless the project has its own pyright config; the language server sets `typeCheckingMode` to `standard` when the editor sends none. History: 0.3.3 (2026-10-05) had a separate `byname.typeCheckingMode` for `.pyn`, so it could run beside the BasedPyright extension (`.py`), plus two more coexistence workarounds (only our command advertised, the extension's default `stubPath: "typings"` dropped). 0.4.0 (2026-10-06) made byname the workspace's only Python server (`.pyn`, `.py`, notebooks), so all three went: one `basedpyright.analysis.*` for every file.
- **Notebooks in the editor (0.4.0):** Jupyter's VS Code extension forces Python-kernel cells to a fixed language list (`python`, `markdown`, `sql`, …; `updateCellLanguages` resets any other on kernel select), so a cell can't be `pyn`; the BasedPyright extension claims `{notebook: "*", language: "python"}` and its `ignore` setting doesn't apply to cells (measured: settings and pyrightconfig.json), hence byname replacing it rather than sitting beside it. The proxy advertises `notebookDocumentSync` for `jupyter-notebook` cells; a notebook with a `%load_ext byname` cell (`LOAD_EXT_RE`) has each cell translated alone (its own prelude, as the kernel runs it) and kept in `docs` by cell uri, which is the same on both sides (basedpyright chains cells itself). Cell edits arrive incremental whatever `textDocumentSync` says (vscode-languageclient's notebook feature), so `apply_changes` applies them and the checker gets each cell whole. Adding/removing the `%load_ext` line resends every cell. Ruff's fixAll isn't offered per cell: unused-import removal would break later cells.
- **basedpyright infers a mixed list as `list[Unknown]`** (`[(age="90"), (age=23)]`, even `[1, "a"]`), unlike pyright's `list[int | str]`. Unknown switches off checking for everything read from it, so `rs[0]._replace(nme=...)` passed silently. byname turns on `strictListInference`, `strictDictionaryInference` and `strictSetInference` with a `# pyright:` comment at the top of the generated prelude (`CHECKER_DIRECTIVE` in `transform.py`), giving `list[A | B]`. A comment, not a setting: these aren't language-server settings (injecting them via `workspace/configuration` silently did nothing), and the checker runs in the user's project, where byname writes no config file. Only files with records get it, and the comment overrides a project config for those files. Output files don't get it. Records can't be told apart at runtime (one class per field set; field types exist only for the checker), so `isinstance(r.age, int)` narrows the field, not the record; to require one type, annotate: `rs: list[(name: str, age: int)] = [...]`.
- **basedpyright config:** it asks for the `python` and `basedpyright` sections, with `analysis` nested inside. It only asks when the client declares `workspace.configuration`; VS Code does.
- **Ruff formatter:** it rejects `__P(a=__p) = x` as an invalid assignment target, but accepts `__P[a:__p] = x`. It writes complex slices as `a : b`, and `decode` strips that spacing.
- **Record methods are attached after the class is made** (`_byname_setup`), in the `else:` branch checkers skip, so nothing is assigned in a NamedTuple body.
- **Grids ride on a comment:** Ruff has no bin-packing option, but it keeps a comment that follows an opening bracket on that line. `grid` tags each grid with `# __grid:<k>` (k = items on its first line). After Ruff, `ungrid` measures the width of those k items as Ruff wrote them and repacks to it, so the result doesn't depend on how the first line was spaced, and a second format changes nothing. Ruff's isort (I001, organize imports) has no packing either and writes a parenthesized import one name per line, so `fix_pyn` / `fix_notebook` end with `regrid_imports`: each `from m import (` that was a grid before the fixes (matched by module, as sorting moves statements) is tagged with its old k and repacked by `ungrid`. A sorted grid then comes back unchanged, so `byname tool` drops an I001 on a file that organizing leaves as it is (`only_grids`); such a file is all-or-nothing: one really unsorted block keeps every I001 in it shown.
- **pyright (basedpyright 1.40.1, pyright 1.1.414) loses the type arguments of a generic tuple subclass when it's star-unpacked into a call:** `fn(*R("a", 1))` with `class R[T0, T1](NamedTuple)` checks each argument as `object`. Upstream bug, not reported. byname used to route every `*x` through a typed identity helper (`_byname_star`) for records; records are no longer tuples to the checker (see "Records are read by name only"), so `fn(*rec)` is an error and the helper is gone.
- **Ruff's maximum `line-length` is 320.** It can't turn wrapping off, and it has no option to keep `a; b` on one line (only `# fmt: skip`).
- **Runtime cost of `.pyn`: none in a training loop** (2026-10-05, RTX 4060, torch 2.13). llm's `src/records/second.pyn` (records for configs, `fn(x=)` keyword calls, pattern parameters) against its plain-Python twin `src/video/minimal.py`, same GPT (block 32, embed 64, 4 heads, 3 layers, batch 32), same seed: identical weights, same loss to 6 decimals, identical evals after 500 steps (train 2.773 / val 2.766), full `train()` about 2.0 s each. Step time differences were within ±4% and flipped sign between two runs (noise), eager and under `torch.compile` (default, fused AdamW, `reduce-overhead`, `max-autotune-no-cudagraphs`): dynamo traces the translated code like any Python, since records and destructuring sit outside `forward`. One-time cost at import: translating that file takes 12 ms (the hook translates on every import: `PynLoader.set_data` writes no `.pyc`, so a cached transform can't go stale when byname changes).

## Design decisions and why

- **`field=value`: the left side is always the field, the right side always the local,** in calls, records and patterns. Renaming is `(name=n) = r`, matching `{ name: n }` in TS.
- **Patterns use parens `(…) = r`, not braces,** matching record literals.
- **No dict syntax.** A dict design was drafted: in braces, `=` for a literal key and `:` keeping its Python meaning (`{name=, age=} = d`, `{key: v} = d`). Dropped because it buys nothing over records, and dict literals lose per-key types (`dict[str, str | int]`).
- **No shorthand in a parameter's default** (`no_default_shorthand`, `def` and `lambda`, any depth). `def f(name=)` would mean "default to the outer `name`", and a function should almost never take outer variables by the same name. The same holds deeper: `def f(user=(name=))`, `dict(name=)` and `lambda x=(name=)` did the same. `name=name` says it. Shorthand in a lambda's body is fine, except when that lambda is itself a default: `def f(name, g=lambda: h(name=))` reads the outer `name` when `g` runs, never `f`'s parameter (the lambda is made outside `f`'s scope), the same misreading, so it's rejected on purpose.
- **Record types are `(name: type, ...)` in annotations,** matching hover's display. Added because recursive functions can't be inferred (pyright treats the recursive call as `Unknown` while inferring), and a record's generated class can't be named in a `.pyn`. Here `:` really is a type annotation, unlike in the rejected `(email: e)` pattern form below. Never valid Python, so no clash: lambdas start with a keyword, walrus is its own `:=` token, and def parameter lists are skipped. Translated by small edits (`(` → `R[`, drop `name:`, `)` → `]`), so nested record types work. Formatter stand-in: `__T[name: type]`.
- **Records are read by name only; order is display.** Positional access (unpacking, `rec[0]`, iterating, `*rec`, `<`) let a reorder where a record is built silently swap same-typed fields at every reader (`x, y = get_batch()` under `-> (x: Tensor, y: Tensor)` returning `(y=…, x=…)` printed `2 1`, 0 errors). So nothing reads a record by position, typed or inferred; return a tuple for positions. **Checker:** `_rec_<fields>` is a function returning the record's exact type, `_typ_<fields>`, the Protocol a written `(name: str, age: int)` is. Protocols match by structure, so the same fields in another order are the same type (`rs.append((age=1, name="a"))` on a list of `(name=, age=)` records), and they have no `__iter__`/`__getitem__`, so pyright reports "not iterable". Measured: a NamedTuple can't be made non-positional (pyright unpacks and indexes it by its tuple element types whatever `__iter__` says); a plain class per written order worked for positions but kept orders apart as types. The Protocol's fields are `Final` (read-only, so immutable records match), plus `_byname_fieldset` (sorted field names as a `Literal`, `'age,name'`), so an extra or missing field is an error on any value, not only fresh literals as in TypeScript; `_replace(...) -> Self`, a typed `_asdict`, `keys()`, `_fields`, `__len__`. byname rewrites pyright's page about `_byname_fieldset` into "extra field: po" / "missing field: name", a type-parameter mismatch (`T1@_typ_name__age is invariant`, same class on both sides) into `"age" is an incompatible type`, and adds `records are read by name: (x=, y=)` to a positional read (`explain_fields`). The proxy puts the fields on that diagnostic (`data.bynameFields`) and answers codeAction with a quick fix: `x, y = rec` / `for x, y in recs` → `(x=, y=)`, matched in the written order (what the positional read meant), `_` dropping its field (`by_name_edit`). **Runtime:** a NamedTuple whose fields are stored sorted by name, so `==` and `hash` are tuple's own on records of one field set in any order (cost measured: same as today; a by-name `__eq__`/`__hash__` without sorted storage was 5–40× slower). `_byname_setup` adds the written order (`_byname_order`) for `repr`, `keys()` (so `**rec`) and `_asdict()`, and an `__eq__` that also requires the same `_fields` and a byname record (never equal to a plain tuple; as a tuple subclass its reflected `__eq__` runs first for `(1, 2) == rec`), about 45 ns per `==`; set after the class is made, because NamedTuple refuses `_asdict` in a body and a body `__eq__` drops tuple's C `__hash__`. Records from different modules are different classes, so equality compares `_fields`, not classes. Positional access raises at runtime too: iterating (so unpacking, `list(rec)`, `json.dumps(rec)`), `rec[0]`, `+`/`*` (`_byname_positional`), and `<`/`<=`/`>`/`>=` return NotImplemented, so `sorted(recs)` raises like it does on dicts. It used to work "because libraries may rely on it", but it read the sorted storage order, which nobody wrote: `a, b = (name="rahul", age=26)` gave `26, "rahul"`, `sorted` ordered by `age` because that name comes first. NamedTuple's own `__getnewargs__` (pickle, copy) and `_replace` iterate, so they're replaced. `in` asks for a field name, as on a dict (it searched the values: `"name" in (name="rahul")` was False); the checker allows it but doesn't narrow, see open_issues.md. `rec["name"]` works at runtime (`**rec` and `dict(rec)` call `keys()` and then `rec[k]`, and making it raise would mean rewriting every `**x` at runtime, against "valid Python is never changed"), and is the checker's unchecked read (see Brackets). `json.dumps(rec)` can't give an object: json writes any tuple subclass as a list without calling a hook, so it raises; `json.dumps({**rec})`. Rejected on the way: allowing positions where the type is inferred (a reorder at the literal still breaks callers silently), and wrapping mixed-order returns in a helper (patches one case).
- **Returned tuples are labelled by name, for hover only.** In the checker translation, `return x, y` in a function with no return annotation becomes `return _byname_tup_x__y(x, y)`, which returns `_tup_x__y[T0, T1]`, a subclass of `tuple[T0, T1]` with no attributes; `pretty()` shows it as `tuple[x: Tensor, y: Tensor]` (`label_returns` / `tuple_def` in `transform.py`). A tuple subclass keeps everything a tuple does in pyright (unpacking, indexing, wrong-arity errors, assignable to `tuple[...]`), measured. A walrus labels its position with the name it binds (`(x := x.to(d), y := y.to(d))`, so a value needn't get its own line to be named). basedpyright calls such a name unused when nothing reads it after (the usual case: a fresh name); the transform records where each one is (`Result.labels`) and both the proxy and `byname tool` drop "is not accessed" there, and nowhere else (`Translation.quiet`). Ruff doesn't flag it. Any other item that isn't a bare name (or whose name has `__` or a leading/trailing `_`, which the class name can't carry) has no label, and a tuple with no labels isn't touched; nor is `return *a, b`, or any `return` under a `-> ...` annotation (what's written is what hover shows, and the wrap would break it: `x = "r"; return x, 1` under `-> tuple[Literal["r", "w"], int]` became a false error, measured). What runs is unchanged. Cost: literal values are widened (`name = "rahul"; return name, age` is `tuple[name: str, age: int]`, plain Python `tuple[Literal['rahul'], Literal[26]]`), because pyright widens literals when it solves a generic call's type parameters; measured the same for a `(t: tuple[T0, T1])` helper and a `*Ts` one. Accepted (see open_issues.md). Why: once records became read-by-name only, `(x=, y=) = get_batch()` was the cost of naming a pair that's unpacked at once; labels document a tuple's order for free. **Not planned: flagging a swapped unpack.** `y, x = get_batch()` can be flagged (measured: a per-target-list helper whose `@deprecated` overload matches a label at another target's position), but only when the caller reuses the returned names: `yb, xb = get_batch()`, the same swap under names of its own (the llm repo unpacks `xb, yb = get_batch(...)`), passes. A check that catches a swap only under matching names is worse than none: it suggests unpacks are checked. Also measured: 124 files of the llm and cp repos had 0 unpacks it would flag. Labels in hover are the defence: the order is visible where the unpack is written.
- **Open record types, `(..., name: str, age: int)`:** any record with at least these fields, with these types. A Protocol (`_opn_<fields>`) with the `Final` fields, `__getitem__`, `__contains__` (see Brackets) and `keys()`, so `**p` and `dict(p)` work (unchecked: the other fields are unknown): no field set, no positional access, no `_asdict` (its real fields are unknown). **`...` goes first** (2026-10-06), and anywhere else in a record type it's an error: a long type split over lines says it's open before its fields, as `*` in `def f(*, name)` changes how the rest reads; it matches the planned function types' `(*, name: str) -> T`, and fields are added at the end with nothing to step around. Every precedent trails (Flow `{ name: string, ... }`, Rust's `{ x, .. }`, OCaml's `< name: string; .. >`), but those come from patterns, where `..` is "the rest"; here it says something about the whole type. `(...)` (or `(...,)`) is the open type with no fields, `_opn_`: any record, read with brackets. It's valid Python (an Ellipsis in parentheses), so it's a type only where a type stands (`type_slot`: after `->`, a parameter's or record field's `:`, `name: T` / `a.b: T` at a statement's start, `type X =`); `x = (...)` and `a[(...)]` are left alone. Its formatter stand-in is `__T[...]` like any record type, else ruff drops the parentheses. Not inside a subscript (`list[(...)]` would collide with numpy's `a[(...)]`). Open types used to match any object with the fields, dataclasses included; with `__getitem__` they match records (and mappings with those attributes) only, since `p["x"]` on a dataclass raises. For functions that read part of a config: `def __init__(self, model: (..., vocab_size: int, n_layer: int), train: (..., dropout: float))` called as `GPT(gpt_cfg, train_cfg)`. Pick per function: `**rec._asdict()` when it must handle every field (it catches "added `dropout`, `GPT` ignores it"); an open type when it reads a subset. One parameter per source config: merging configs isn't typeable (`{**a._asdict(), **b._asdict()}` is `dict[str, int | object | float]`, a merged type is an intersection). Nesting works: `(model=gpt_cfg, train=train_cfg)` against `(..., model: (…), train: (…))`.
- **Brackets are the unchecked read: `rec.name` is checked, `rec["name"]` isn't** (2026-10-06). Every record type, exact or open, has `__getitem__(self, k: _key_<fields>, /) -> Any`: any string key, typed `Any`, `KeyError` at runtime if the field isn't there. It gets around the checker where it can't follow: an open type's other fields (`if "title" in p: p["title"]`), a union of records, which `in` doesn't narrow (open_issues.md). TypeScript's `noPropertyAccessFromIndexSignature` makes the same split. Always `Any`, even for a key that is a field of an exact type: a precise type there would make brackets sometimes checked, blurring the split. `k` is typed `_key_<fields>`, a `type` alias of `str` per field set, so that pyright's complaint about `rec[0]` names the record (a bare `str` gives only `"Literal[0]" is not assignable to "str"`, measured) and `explain_fields` can add `records are read by name: (x=, y=)` and print the alias as `"str"`.
- **Fields read through a record type are coloured like record fields.** pyright gives a NamedTuple field `static`, a `@property` `readonly`, a `Final` attribute `readonly static`; themes colour `readonly` differently. `Final` (not `@property`) gives a pair that's otherwise rare, and the proxy drops `readonly` from `property` tokens carrying both, so `p.age` and `u.age` match. Measured: a descriptor-typed Protocol member (`age: _F[int]`) doesn't match NamedTuple fields at all.
- **`deepdict(rec)`, not `_asdict(deep=True)`** (2026-10-18): `_asdict()`, `dict(rec)` and `{**rec}` stay one level like NamedTuple's, and `deepdict` (runtime.py) turns a record into a dict with every record inside it a dict too, recursing into exact lists, tuples and dict values; anything else is left as it is, so a NamedTuple or a tensor isn't touched. A function, not a flag: it keeps `_asdict` NamedTuple's and reads as the inverse of `record(T, d)`. **The name:** `plain` said nothing (the shape doesn't change, only records become dicts), `to_builtins` promised builtins all the way down though tensors stay, `to_dict` didn't say it goes deeper than `dict(rec)`, `asdict` would sit next to the one-level `_asdict`. `deepdict` borrows `copy`/`deepcopy`: `dict(rec)` one level, `deepdict(rec)` every level. **A record at the top only:** so the name is true for every input and the type is always `dict[str, Any]`, with no `Any` fallback; a list or a NamedTuple is a checker error (the parameter is a protocol with `keys() -> tuple[str, ...]`, which only records have: a dict's keys() is a view, a NamedTuple has none, open types match too) and a `TypeError`. A list of records is a comprehension. `record()` builds the records in `list[R]`, `tuple[R, ...]` and `dict[K, R]` fields for the round trip; other generics stay shallow. A precise type, `deepdict(cfg)["schedule"]["max_lr"]` as `float`, can't be written generically; see Not yet built. Either spelling would have needed it, so typing didn't pick between them.

- **Rest patterns, `(name=, **rest) = r`: why kept (2026-10-23).** Removal was considered: across diffusion-final, asr, world-model-final and llm-final (82 `.pyn` files) there were two uses, both replaceable (diffusion's `flat_config`, a workaround its TODO retires with `deepdict`; a test in llm-final faking an old checkpoint, `_asdict()` plus `del` would do), and rest cost the omit overloads (since replaced, see the next entry), the runtime `_byname_omit` and its editor handling. - **`record(T, d)`, a function, not syntax (2026-10-07).** A dict loaded from a file had no checked way into a record: `(**d)` is rejected by the checker (a dict's keys aren't known statically) and at runtime builds whatever keys `d` has (`(**{"name": "r"})` into `(name: str, age: int)` gave `(name='r')`); building field by field checks names only, one line per field. `record(T, d)` checks names and types at runtime and is typed `T` for the checker. ## Not yet built

**Designed, not built:**
- **Spreads in record types, `type Run = (**ModelConfig, **TrainConfig, seed: int)`**: every field of both, plus `seed`, for combining types without copying field lists (TS `ModelConfig & TrainConfig & { seed: number }`). A leading `...` keeps it open as usual. Today `(**T, name: str)` is a syntax error ("a record built from spreads takes `**record` and `name=value` items"). Plan: expand the text before translating, `(..., **TrainConfig, name: str)` → `(..., batch_size: int, lr: float, name: str)`, so the checker only ever sees a plain record type and errors and hovers work unchanged. Limits: the alias must be a record-type `type` alias in the same file (an imported one is an error, not `Any`); a field in two parts is an error, not an override; aliases that spread aliases expand in order. Not for a function's own parameter type: `(..., **TrainConfig)` there requires all of `TrainConfig`, same as `: TrainConfig`, which is why llm's `train`/`GPT` write their fields inline.
- **Precise types for `deepdict(rec)`** (tier 2): `deepdict(cfg)["schedule"]["max_lr"]` as `float`, not `Any`. One overload per record type the file names, each returning a `_pln_<Type>` TypedDict built from its written fields (`schedule: _pln_Schedule`, `history: list[_pln_EvalRow]`), generated only in files that import `deepdict`; a record with no named type falls back to `dict[str, Any]`. Needs the transform to rewrite each type's field annotations, handle inline nested record types and follow imported types through the lookup: roughly 100–150 lines. Build it if reading plain dicts by key turns out common.
- **Function types, `encode: (s: str) -> list[int]`, `greet: (*, name: str, age: int) -> None`** (TS `(s: string) => number[]`). Today `(s: str)` parses as a record type and the `->` is a syntax error. `Callable[[str], list[int]]` works for positional parameters but drops their names (hover, keyword calls through a parameter). **Keyword-only functions, byname's usual style, can't be typed with `Callable` at all** (measured 2026-10-05): `def fn(*, name: str, age: int)` isn't assignable to `Callable[[str, int], None]`, and `Callable[..., None]` accepts it but checks nothing (`b(nme="x")` passed). The only way today is a hand-written Protocol, `class Greet(Protocol): def __call__(self, *, name: str, age: int) -> None: ...`, which checks calls (`c(name="rahul")` → missing `age`). Plan: `(params) -> T` is unambiguous (a record type is never followed by `->`) and would translate for the checker to exactly that Protocol, with the parameter list copied as written (`*`, defaults, `/`). Not built yet (2026-10-05): only needed where such a function is passed as a value or stored in a record field; first real use was a `type CharTokenizer = (vocab_size: int, encode: ..., decode: ...)` alias in llm's `src/records/second.pyn`. Tracked in open_issues.md.

**Ruled out along the way:**
- **Partial cast `cast((..., age: int), r)`**, meaning "same record, `age` now `int`": needs an intersection type. Use a full `cast((name: str, age: int), r)`; it's checker-only, like TypeScript's `as`.
- **A generic merge, `a.merge(b)` or `def merge[A, B](a: A, b: B) -> A & B`**: the merged type of two unknown types is an intersection. Spreads (below) work instead because the target type is known where the record is used, or the result is `Any`.
- **Narrowing a record by a field:** `isinstance(r.age, int)` narrows `r.age`, not `r`, so `r._replace(age=99)` on a mixed union still fails. Keep record lists to one type, or annotate them (`rs: list[(name: str, age: int)] = [...]`). A `Literal` tag does narrow (measured 2026-10-09): with `kind: Literal["square"]` in one record and `kind: Literal["circle"]` in the other, `if s.kind == "square":` and `match s.kind:` give each branch one record type, and overloads on the two types pick by shape (`test_a_literal_tag_narrows_a_union_of_records` in test_exhaustive.pyn).
- **`**` of a union of records:** with a mixed list, `fn(**rs[0]._asdict())` is flagged even when `fn` accepts both types, because basedpyright unpacks a union of TypedDicts as `object` values. Same remedy: one type per list.

## Conventions

- **Python versions in the checker:** byname's own venv is 3.14, where annotations may name classes defined further down; users' projects (llm: 3.12) aren't. 21f1394 emitted each record's checker function before the `_typ_` Protocol it returns, so on 3.12 every record was `Unknown` and the undefined names were hidden as generated-code diagnostics. Fixed 2026-10-05 (types first); `test_records_are_typed_on_python_before_3_14` pins `pythonVersion` 3.12.
- **Tests:** `uv run pytest`. They're written to explain the behaviour, with real values in the asserts. `test_lsp.py`, `test_tools.py` and `test_fmt.py` drive the real basedpyright and Ruff, and skip if those aren't installed.
- **Every feature goes in `tests/test_exhaustive.pyn`:** it's the one walkthrough of everything byname enables, read top to bottom. A new or changed feature gets a test there in its section (runtime behaviour, the translation where it explains the feature, the checker's verdict through `checker()` when the point is typing, and its errors), in the same change as the code. Edge cases go in `test_transform.py` and friends; test_exhaustive shows what a user can write.
- **Extension changes:** bump `version` in `editors/vscode/package.json`, rebuild with `vsce package …`, then `code --install-extension byname.vsix --force` and Reload Window. Server-only changes just need Reload Window, since `.venv` is an editable install.
- **Measure before proposing:** several plausible mechanisms turned out false in practice, such as Ruff accepting call stand-ins.
