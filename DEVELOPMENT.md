**What the port settled on** (shapes for torch code in `.pyn`):
- **Configs are records** with `type GPTConfig = (...)` aliases (closed: exact fields) at the top. Functions take them through parameter patterns with inline open types: `def __init__(self, (vocab_size=, ...): (vocab_size: int, ..., ...))`, called as `GPT(gpt_cfg)`.
- **Defaults hold only size-independent fields** (`train_defaults = (eval_interval=100, eval_iters=100)`); each config spreads them and must set the size-dependent ones: `train_cfg: TrainConfig = (**train_defaults, batch_size=32, ...)`. `_replace` from a full config was rejected: a stale `block_size` rides along silently. The annotation is what checks a config against its closed type; an unannotated spread of known names is still typed (see Spreads).
- **`nn.Module.__call__` is `Callable[..., Any]`,** so `model(x)` is `Any`. `GPT` gets a checker-only `if TYPE_CHECKING: def __call__(self, idx: Tensor) -> Tensor: ...` (`__call__ = forward` doesn't work: the base's declared type wins). Calls to torch's own layers inside `forward` get one annotation at the first local (`qkv: Tensor = self.qkv(x)`); einops' `rearrange` is generic, so types flow through it.

**Global VS Code config** (`~/.config/Code/User/`):
- `keybindings.json` has **Alt+R** for `.pyn`: save, then `uv run byname run "${file}"` in the terminal, with `VIRTUAL_ENV` pinned.
- **Alt+C** (write output) was added and then removed; output-on-save replaced it.
- `settings.json` has global `editor.formatOnSave: true`, but `false` for `[python]`. `.pyn` isn't `[python]`, so `.pyn` files format on save.
- `"ruff.lint.enable": false`, so the Ruff extension doesn't lint in the editor; only the Alt+L task does.

## Measured facts (don't re-measure)

- **Return-type inference through the translation:** pyright, basedpyright and Pyrefly give identical results (`-> _rec_…[str, int]`, field types, and an error on unknown fields). ty returns `Unknown` everywhere.
- **Checkers (2026-10-05): basedpyright (and pyright) is the only supported checker;** byname is designed and tested against it. Every other checker (mypy, Pyrefly, ty) is not supported: no workarounds, no tests, no docs. mypy was also dropped from `byname tool`'s docs and the dev dependencies, and its workarounds were removed from the translation (2026-10-05: the `if MYPY:` branch, the `Any` default on `_byname_ctx`'s TypeVar, `# type: ignore` comments; basedpyright's output on every `.pyn` in the repo was unchanged). The proxy can still run another checker (`byname.checker`), unsupported. Measured on 2026-10-04, kept for reference: a 29-case matrix of every feature, each line tagged as an expected error or not:
  - basedpyright 1.40.1: all right.
  - Pyrefly 1.3.2: misses errors in all 4 spread-built records (`p: T = (**u,)`, `f((**u,))`, `f(p=…)`, overloads), never a false error: it doesn't give a lambda's parameter the expected type, so they're unchecked. Everything else matches basedpyright.
- **basedpyright's default mode is noisy:** "recommended" flags `reportImplicitRelativeImport` and similar. `byname tool` uses `standard`, unless the project has its own pyright config. The language server uses the `byname.typeCheckingMode` setting (default `standard`, sent in `initializationOptions`) and ignores the editor's `basedpyright.analysis.typeCheckingMode`: that one is for `.py` files, and with the BasedPyright extension installed it always arrives (its default, `recommended`), so a default-only rule never applied (2026-10-05). So `.py` and `.pyn` can run in different modes (llm: `.py` off, `.pyn` standard). A project pyright config overrides both, as basedpyright prefers it to editor settings.
- **basedpyright infers a mixed list as `list[Unknown]`** (`[(age="90"), (age=23)]`, even `[1, "a"]`), unlike pyright's `list[int | str]`. Unknown switches off checking for everything read from it, so `rs[0]._replace(nme=...)` passed silently. byname turns on `strictListInference`, `strictDictionaryInference` and `strictSetInference` with a `# pyright:` comment at the top of the generated prelude (`CHECKER_DIRECTIVE` in `transform.py`), giving `list[A | B]`. A comment, not a setting: these aren't language-server settings (injecting them via `workspace/configuration` silently did nothing), and the checker runs in the user's project, where byname writes no config file. Only files with records get it, and the comment overrides a project config for those files. Output files don't get it. Records can't be told apart at runtime (one class per field set; field types exist only for the checker), so `isinstance(r.age, int)` narrows the field, not the record; to require one type, annotate: `rs: list[(name: str, age: int)] = [...]`.
- **basedpyright config:** it asks for the `python` and `basedpyright` sections, with `analysis` nested inside. It only asks when the client declares `workspace.configuration`; VS Code does.
- **Ruff formatter:** it rejects `__P(a=__p) = x` as an invalid assignment target, but accepts `__P[a:__p] = x`. It writes complex slices as `a : b`, and `decode` strips that spacing.
- **Record methods are attached after the class is made** (`_byname_setup`), in the `else:` branch checkers skip, so nothing is assigned in a NamedTuple body.
- **Grids ride on a comment:** Ruff has no bin-packing option, but it keeps a comment that follows an opening bracket on that line. `grid` tags each grid with `# __grid:<k>` (k = items on its first line). After Ruff, `ungrid` measures the width of those k items as Ruff wrote them and repacks to it, so the result doesn't depend on how the first line was spaced, and a second format changes nothing.
- **pyright (basedpyright 1.40.1, pyright 1.1.414) loses the type arguments of a generic tuple subclass when it's star-unpacked into a call:** `fn(*R("a", 1))` with `class R[T0, T1](NamedTuple)` checks each argument as `object`. Upstream bug, not reported. byname used to route every `*x` through a typed identity helper (`_byname_star`) for records; records are no longer tuples to the checker (see "Records are read by name only"), so `fn(*rec)` is an error and the helper is gone.
- **Ruff's maximum `line-length` is 320.** It can't turn wrapping off, and it has no option to keep `a; b` on one line (only `# fmt: skip`).
- **Runtime cost of `.pyn`: none in a training loop** (2026-10-05, RTX 4060, torch 2.13). llm's `src/records/second.pyn` (records for configs, `fn(x=)` keyword calls, pattern parameters) against its plain-Python twin `src/video/minimal.py`, same GPT (block 32, embed 64, 4 heads, 3 layers, batch 32), same seed: identical weights, same loss to 6 decimals, identical evals after 500 steps (train 2.773 / val 2.766), full `train()` about 2.0 s each. Step time differences were within ±4% and flipped sign between two runs (noise), eager and under `torch.compile` (default, fused AdamW, `reduce-overhead`, `max-autotune-no-cudagraphs`): dynamo traces the translated code like any Python, since records and destructuring sit outside `forward`. One-time cost at import: translating that file takes 12 ms (the hook translates on every import: `PynLoader.set_data` writes no `.pyc`, so a cached transform can't go stale when byname changes).

## Design decisions and why

- **`field=value`: the left side is always the field, the right side always the local,** in calls, records and patterns. Renaming is `(name=n) = r`, matching `{ name: n }` in TS.
- **Patterns use parens `(…) = r`, not braces,** matching record literals.
- **No dict syntax.** A dict design was drafted: in braces, `=` for a literal key and `:` keeping its Python meaning (`{name=, age=} = d`, `{key: v} = d`). Dropped because it buys nothing over records, and dict literals lose per-key types (`dict[str, str | int]`).
- **No shorthand in `def` signatures.** `def f(name=)` would mean "default to the outer `name`", and a function should almost never take outer variables by the same name.
- **Record types are `(name: type, ...)` in annotations,** matching hover's display. Added because recursive functions can't be inferred (pyright treats the recursive call as `Unknown` while inferring), and a record's generated class can't be named in a `.pyn`. Here `:` really is a type annotation, unlike in the rejected `(email: e)` pattern form below. Never valid Python, so no clash: lambdas start with a keyword, walrus is its own `:=` token, and def parameter lists are skipped. Translated by small edits (`(` → `R[`, drop `name:`, `)` → `]`), so nested record types work. Formatter stand-in: `__T[name: type]`.
- **Records are read by name only; order is display.** Positional access (unpacking, `rec[0]`, iterating, `*rec`, `<`) let a reorder where a record is built silently swap same-typed fields at every reader (`x, y = get_batch()` under `-> (x: Tensor, y: Tensor)` returning `(y=…, x=…)` printed `2 1`, 0 errors). So nothing reads a record by position, typed or inferred; return a tuple for positions. **Checker:** `_rec_<fields>` is a function returning the record's exact type, `_typ_<fields>`, the Protocol a written `(name: str, age: int)` is. Protocols match by structure, so the same fields in another order are the same type (`rs.append((age=1, name="a"))` on a list of `(name=, age=)` records), and they have no `__iter__`/`__getitem__`, so pyright reports "not iterable". Measured: a NamedTuple can't be made non-positional (pyright unpacks and indexes it by its tuple element types whatever `__iter__` says); a plain class per written order worked for positions but kept orders apart as types. The Protocol's fields are `Final` (read-only, so immutable records match), plus `_byname_fieldset` (sorted field names as a `Literal`, `'age,name'`), so an extra or missing field is an error on any value, not only fresh literals as in TypeScript; `_replace(...) -> Self`, a typed `_asdict`, `keys()`, `_fields`, `__len__`. byname rewrites pyright's page about `_byname_fieldset` into "extra field: po" / "missing field: name", a type-parameter mismatch (`T1@_typ_name__age is invariant`, same class on both sides) into `"age" is an incompatible type`, and adds `records are read by name: (x=, y=)` to a positional read (`explain_fields`). The proxy puts the fields on that diagnostic (`data.bynameFields`) and answers codeAction with a quick fix: `x, y = rec` / `for x, y in recs` → `(x=, y=)`, matched in the written order (what the positional read meant), `_` dropping its field (`by_name_edit`). **Runtime:** a NamedTuple whose fields are stored sorted by name, so `==` and `hash` are tuple's own on records of one field set in any order (cost measured: same as today; a by-name `__eq__`/`__hash__` without sorted storage was 5–40× slower). `_byname_setup` adds the written order (`_byname_order`) for `repr`, `keys()` (so `**rec`) and `_asdict()`, and an `__eq__` that also requires the same `_fields` and a byname record (never equal to a plain tuple; as a tuple subclass its reflected `__eq__` runs first for `(1, 2) == rec`), about 45 ns per `==`; set after the class is made, because NamedTuple refuses `_asdict` in a body and a body `__eq__` drops tuple's C `__hash__`. Records from different modules are different classes, so equality compares `_fields`, not classes. Positional access raises at runtime too: iterating (so unpacking, `list(rec)`, `json.dumps(rec)`), `rec[0]`, `+`/`*` (`_byname_positional`), and `<`/`<=`/`>`/`>=` return NotImplemented, so `sorted(recs)` raises like it does on dicts. It used to work "because libraries may rely on it", but it read the sorted storage order, which nobody wrote: `a, b = (name="rahul", age=26)` gave `26, "rahul"`, `sorted` ordered by `age` because that name comes first. NamedTuple's own `__getnewargs__` (pickle, copy) and `_replace` iterate, so they're replaced. `in` asks for a field name, as on a dict (it searched the values: `"name" in (name="rahul")` was False); the checker allows it but doesn't narrow, see open_issues.md. `rec["name"]` still works at runtime (only the checker rejects it): `**rec` and `dict(rec)` call `keys()` and then `rec[k]`, and making it raise would mean rewriting every `**x` at runtime, against "valid Python is never changed". `json.dumps(rec)` can't give an object: json writes any tuple subclass as a list without calling a hook, so it raises; `json.dumps({**rec})`. Rejected on the way: allowing positions where the type is inferred (a reorder at the literal still breaks callers silently), and wrapping mixed-order returns in a helper (patches one case).
- **Returned tuples are labelled by name, for hover only.** In the checker translation, `return x, y` in a function with no return annotation becomes `return _byname_tup_x__y(x, y)`, which returns `_tup_x__y[T0, T1]`, a subclass of `tuple[T0, T1]` with no attributes; `pretty()` shows it as `tuple[x: Tensor, y: Tensor]` (`label_returns` / `tuple_def` in `transform.py`). A tuple subclass keeps everything a tuple does in pyright (unpacking, indexing, wrong-arity errors, assignable to `tuple[...]`), measured. A walrus labels its position with the name it binds (`(x := x.to(d), y := y.to(d))`, so a value needn't get its own line to be named). basedpyright calls such a name unused when nothing reads it after (the usual case: a fresh name); the transform records where each one is (`Result.labels`) and both the proxy and `byname tool` drop "is not accessed" there, and nowhere else (`Translation.quiet`). Ruff doesn't flag it. Any other item that isn't a bare name (or whose name has `__` or a leading/trailing `_`, which the class name can't carry) has no label, and a tuple with no labels isn't touched; nor is `return *a, b`, or any `return` under a `-> ...` annotation (what's written is what hover shows, and the wrap would break it: `x = "r"; return x, 1` under `-> tuple[Literal["r", "w"], int]` became a false error, measured). What runs is unchanged. Cost: literal values are widened (`name = "rahul"; return name, age` is `tuple[name: str, age: int]`, plain Python `tuple[Literal['rahul'], Literal[26]]`), because pyright widens literals when it solves a generic call's type parameters; measured the same for a `(t: tuple[T0, T1])` helper and a `*Ts` one. Accepted (see open_issues.md). Why: once records became read-by-name only, `(x=, y=) = get_batch()` was the cost of naming a pair that's unpacked at once; labels document a tuple's order for free. **Not planned: flagging a swapped unpack.** `y, x = get_batch()` can be flagged (measured: a per-target-list helper whose `@deprecated` overload matches a label at another target's position), but only when the caller reuses the returned names: `yb, xb = get_batch()`, the same swap under names of its own (the llm repo unpacks `xb, yb = get_batch(...)`), passes. A check that catches a swap only under matching names is worse than none: it suggests unpacks are checked. Also measured: 124 files of the llm and cp repos had 0 unpacks it would flag. Labels in hover are the defence: the order is visible where the unpack is written.
- **Open record types, `(name: str, age: int, ...)`:** any object with at least these fields, with these types. A Protocol (`_opn_<fields>`) with just the `Final` fields: no field set, no positional access, no `_asdict` (its real fields are unknown). Matches records, dataclasses, any object. The trailing `...` follows Flow (`{ name: string, ... }`), Rust's `{ x, .. }` and Python's own `tuple[int, ...]`. For functions that read part of a config: `def __init__(self, model: (vocab_size: int, n_layer: int, ...), train: (dropout: float, ...))` called as `GPT(gpt_cfg, train_cfg)`. Pick per function: `**rec._asdict()` when it must handle every field (it catches "added `dropout`, `GPT` ignores it"); an open type when it reads a subset. One parameter per source config: merging configs isn't typeable (`{**a._asdict(), **b._asdict()}` is `dict[str, int | object | float]`, a merged type is an intersection). Nesting works: `(model=gpt_cfg, train=train_cfg)` against `(model: (...), train: (...), ...)`.
- **Fields read through a record type are coloured like record fields.** pyright gives a NamedTuple field `static`, a `@property` `readonly`, a `Final` attribute `readonly static`; themes colour `readonly` differently. `Final` (not `@property`) gives a pair that's otherwise rare, and the proxy drops `readonly` from `property` tokens carrying both, so `p.age` and `u.age` match. Measured: a descriptor-typed Protocol member (`age: _F[int]`) doesn't match NamedTuple fields at all.
- **Destructuring in parameters: `def f((name=, age=): User)`.** Python 3 has no destructuring parameters (PEP 3113), so the parameter becomes `_byname_p0: User` and `_ds = _byname_p0; name = _ds.name; age = _ds.age` (the same code as `(name=, age=) = r`) goes on a line of its own before the body, after a docstring; all pattern parameters of one `def` share that line. A one-line body gets it before the body with `; ` instead. The extra line lets the body start with `if`/`for`/`try` (the alternative, prefixing the first body line with `;`, can't), and `to_code` maps line numbers back at the AST level (`Result.inserted`): generated lines count as the `def` line, so a bad field's AttributeError points at the pattern. Output files don't care; the checker maps through edits. The formatter stand-in is `__D: (__P[...], T)` (`(__P[...],)` with no type), a valid annotated parameter; when ruff splits that tuple, its lines are dedented one step. Hovers show `_byname_p0` as `(...)`. Named form `user=(name=, age=): User` (`user: User`, the same unpacking from `user`), which can be passed by keyword; it reads like the nested pattern `(user=(name=)) = x`. Its type is optional, `user=(name=) = default` too: inside a signature, a group made only of pattern items (`is_pattern_group`) is always a pattern, so shorthand never means "default to the outer variable" there (it was never meant to; nothing in ~/Documents/codes used it), and a default record mixing `name=` with values is an error (`no_shorthand`). Stand-in `user: (__D, __P[...], T)`, no trailing comma untyped (ruff would keep a 2-tuple split). The unnamed form can't be passed by keyword; lambdas aren't supported (no statement to unpack in).
- **Spreads: `f(**rec)`, `{**rec}`, and records built from spreads `(**u, **r, age=27)`.** `**` means "by name" in Python, `*` "by position"; `(*u, *r)` stays a plain tuple. At runtime records are mappings by field name: every record class has `keys()` and `rec["name"]` (`_byname_keys` / `_byname_item`), so Python's own `**` works on them, and valid Python is never rewritten for what runs. `keys` is a reserved field name for it. For the checker only, `**x` becomes `**_byname_kw(x)`, overloaded to give a record's typed `_asdict()` TypedDict (and pass dicts through), so `fn(**u, **r)` is checked field by field (missing, extra, wrong type; a field in both is "multiple values"). A spread record is `_byname_rec({**u, **r, 'age': 27})`, built from a dict display: a later field wins and keeps the first one's position, like `{**a, **b}` and JS `{...a, ...b}`; repeating a field you wrote yourself is still an error. For the checker, a spread record is checked against the type expected where it stands: `_byname_ctx(lambda t: _byname_check(lambda: t)({…}))`, with `def _byname_ctx(f: Callable[[T], object]) -> T` (PEP 695 `T`). Pyright's expected-type inference solves `T` from the call argument, keyword argument, annotation, `return` under `-> T`, list item, etc., and gives the lambda's parameter that type; `_byname_check` takes T's `_asdict` TypedDict and checks the dict display against it. What runs is plain `_byname_rec({…})`. Measured on the way there: a generic `def f[T](d: Dict[T]) -> T` checks nothing, because pyright retries a call that fails with its expected type *without* it and keeps that; an error inside a lambda's body doesn't fail the call, so the check stays. Pulling the k-th parameter's type out of `fn` (`Callable[Concatenate[A, ...], object]`) also worked but not for keyword arguments to positional-or-keyword parameters (a keyword-matching Protocol rejects them). Overloads: a record that took any expected type made the first overload win, `f(x: int)` included (right record: wrong overload; wrong record: no error). So a whole call argument (`is_argument`) gets `_byname_arg` instead: its TypeVar is bound to `_byname_HasDict[Any] | None` with default `_byname_AnyRec` (a tuple with `_asdict()` and `Any` attributes, shown as `(...)` in hovers). Expected `int` breaks the bound, pyright retries without it, gets `_byname_AnyRec`, `int` rejects it, and the `Person` overload is tried. Elsewhere (`x = (**u)`) it's `_byname_ctx`, with no default, else `fn(x)` would be an error. `_byname_R` uses `typing_extensions`' `TypeVar` for its default because the PEP 696 syntax needs 3.13. Inline `(name: str, …)(**u, **r)` is `_cast(T, _byname_rec(_byname_check(lambda: _cast(T, _byname_anyv))({…})))`: `cast` makes checkers read `T` as a type (aliases and imported names included); the lambda never runs. Open types have no `_asdict`, so they fall to an unchecked overload. Also measured: `type` aliases can't be called; a Protocol with a metaclass `__call__` can't be instantiated by either checker; passing an alias as a value to a generic helper fails (`TypeAliasType`). The rejected first version wrapped every `**x` in calls at runtime too, which changed valid Python (the stdlib round-trip test caught it).
- **Spreads of known names are plain records for the checker** (`known_fields` / `known_build` in `transform.py`). The checker translation runs twice when a file builds spread records: the first pass is parsed, and a name counts as known when it's bound exactly once in the whole file (any scope, any binding form: assignment, parameter, import, `for`, `except`, `match`, `global` all count) and that binding shows its fields: a record literal (`_rec_…(a=…)` keywords), a spread record of known names, or an exact record type (inline, `type` alias, a parameter's annotation; open `...` types don't say which fields). The second pass builds a spread made only of such names as `_rec_a__b__z(a=u.a, b=u.b, z=1)`, so it has its exact type with no type expected, and the field types come from the checker through the attribute reads. A later item wins and keeps the first position, as at runtime; an explicit field overridden by a later spread, a spread whose fields are all overridden, or any unknown spread falls back to the generic path. Rejected alternatives: scoping names properly (more code, and a wrong field set is worse than `Any`, so "bound once anywhere" is the conservative rule); a generic merge (needs an intersection type). Editor side: `**u` becomes `name=` + the user's own `u` + `.name, age=u.age`, so `u` stays real text (colour, hover, rename; replacing it whole left it uncoloured), and written field names are emitted as generated text so byname's record-field colour wins over the checker's keyword-argument one, as on the generic path; `test_spread_names_and_fields_keep_their_colours` checks both through the server. Knock-on fixed in the generic path: a function returning a spread record used to return `Any`; typed, a name bound to it and to a record elsewhere became a union, and inside the generic path's lambda pyright drops narrowing for a name reassigned later, so `fn(user=(**u, **r))` saw the union and failed (`object` values). Spread names are now read through lambda defaults, evaluated where the record stands: `lambda _byname_t, _byname_s0=_byname_kw(r): ...{**_byname_pick(r, _byname_s0)}` (`_byname_pick` returns its second argument's type; the user's `r` stays in place). Only plain names are hoisted. What runs is unchanged. The cost of the switch: a wrong-typed field in an annotated spread is now reported as a record-vs-protocol mismatch (as for a record literal) rather than the shorter TypedDict message, and an overloaded call gets pyright's "no overloads match" alongside the field error.
- **Record types in output files** are plain stand-in classes with `__class_getitem__` returning the class, so `R[int, str]` evaluates on PyPy 3.10, where annotations are evaluated eagerly; no Protocol.
- **Scope: byname adds binding by name and nothing else.** Every form is `name=` (in calls, records and patterns), or the record type that annotates the result. General-purpose syntax that happens to be convenient is out of scope, even next to a pattern.
- **No defaults in patterns, `??` included.** `(email= ?? "none") = user` was designed and dropped. `??` is a general null-coalescing operator, not a binding form. [PEP 505](https://peps.python.org/pep-0505/) is deferred, not rejected, so if Python ever adds `??` with different meaning or precedence, byname would clash with real Python. (`name=` can't clash that way, since PEP 736 was rejected.) Records always have their fields, so a default only matters for an `Optional` field, and the plain-Python line is short: `email = user.email if user.email is not None else "none"`.
- **TS-style `(email: e = "x")` was rejected for defaults and renaming.** `:` reads as a type annotation in Python (the TS `{ name: string }` trap), and it would make building use `=` while taking apart used `:`.
- **No trailing comma required on a single-field record.** Unlike `(x)`, `(x=)` can't be read as grouping, so a comma would only be noise.
- **Positional items in patterns are left an error.** Reading A, where a bare name means by-name, conflicts with Python's `(a, b) = r`, which is positional. Reading B, positional first and then keywords like a call, is consistent, but it brings back the field-order fragility that by-name avoids, and only records support it. Not planned.
- **`for (a=, b=t) in xs:` becomes `for (a, t) in ((_ds.a, _ds.b) for _ds in xs):`**, on one line so line numbers hold. A generator, not binds at the top of the body: the body's first statement may be compound (`a = …; if …:` is invalid), and the generator keeps exact field types and scopes `_ds`. The same rewrite covers comprehension `for` clauses. The iterable ends at the statement's `:`, or for a comprehension at the next `if`/`for`/`async` or the closing bracket. A bare tuple iterable (`in a, b`) is parenthesised; `async for` gets an async generator. Costs a generator per loop, which is fine for judges' time limits but not free.
- **Nested patterns read through chains:** `(user=(name=)) = r` binds `name = _ds.user.name`, with no temporary per level. A `field=(...)` value is a nested pattern only if the group holds a `field=` item; `(x=(a)) = r` stays a parenthesised target. In a `for` target the nested parens stay in the tuple target and the generator's element mirrors them.
- **Records are generic,** so checkers infer exact field types without annotations (a generic Protocol for the checker, a generic NamedTuple at runtime). Each file generates its own classes; at runtime records from two files are different classes, and equality still works (it compares field sets); to the checker they're structurally the same type.
- **Ctrl+click on shorthand `x=` goes to the local** (the implicit value); Go to Declaration goes to the parameter. A shortcut for Declaration was skipped as rarely needed.
- **The editor uses a language-server proxy,** not a piggyback on Pylance, so the checker can be swapped (unsupported; Pyrefly ran) and it works outside VS Code. Pylance itself can't sit behind a proxy because it's closed-source.
- **Hidden translations go in `~/.cache/byname/<hash>`,** not the project, so there's nothing to gitignore.
- **Completion in an empty pattern slot** uses a temporary text: the slot is filled with `_ds.<prefix>` (plus a dummy `x=` item so `(x) = y` counts), the checker is asked, then the real text is restored. The proxy numbers document versions itself, so diagnostics computed on the temporary text are dropped.
- **Output files are named `<name>.pyn.py`,** following the `foo.min.js` convention. They sort right after their source, and the gitignore pattern `*.pyn.py` can't hide a hand-written file.
- **Every output file gets the marker line and the `# ---- <name>.pyn ----` divider,** even with no generated header, so every output file has the same shape.
- **Output-on-save lives in the server's didSave handler,** not the extension, so it works in any editor. It's off by default: projects that run `.pyn` through byname (like llm does) don't need output files. A `byname build --out-dir` (like `tsc --outDir`) is only for publishing to places without byname, and isn't built.
- **`outputStripMain` is off by default** and on in `cp` only.
- **`diagnosticsOnSave` holds the checker's diagnostics in the proxy** until the editor version they were computed for is the saved one, then sends them (on save, or on arrival if the save came first). While the text is unsaved it still sends the shown ones that survive (matched by message, code and severity, since positions move), so a fixed error disappears at once and only new ones wait. On in `cp`, where half-typed code covered the file in red. VS Code moves the squiggles already shown along with edits, so they stay roughly in place while typing. The proxy removes the client's pull-diagnostics capability (`textDocument.diagnostic`) in `initialize`: basedpyright registers pull diagnostics when VS Code offers them, and pulled results would skip `diagnostics()` (the first version of this setting failed in the editor because of that). There's no debounce option: the user wanted "nothing until I save", and holding diagnostics in the proxy works with any checker.
- **Lint fixes run on the translation, not the formatter's stand-ins.** Stand-ins turn `f(os=)` into `f(os=__p)`, so `import os` would look unused and F401 would delete it. On the translation every use is real. A fix is applied only if each of its edits maps back to source text that matches the hidden text exactly; anything touching generated code or the prelude is dropped whole. It loops until nothing changes, because fixes unlock others (`List[int]` → `list[int]` leaves `from typing import List` unused). Only `safe` fixes, like Ruff's own on-save.
- **The server answers `textDocument/codeAction` itself only when `only` is all `source.fixAll*` or all `source.organizeImports*`** (what `codeActionsOnSave` sends); other code-action requests still go to the checker. Organize imports is `--select I001`, as in the Ruff extension.
- **Output files use portable record classes** (`class R(_NT):` with `object` fields, Python 3.6+), because judges' PyPy is 3.10 and rejects `class R[T0](...)`. The checker's translation keeps the 3.12 generic classes, since that's where field types come from.
- **`_replace` and `_asdict` are typed for the checkers only.** NamedTuple types them `(**kwargs: Any)` and `dict[str, Any]`, so `r._replace(n=90)` and a stale `GPT(**cfg._asdict())` passed silently. Each record has a checkers' version (`if _t.TYPE_CHECKING:` ... `else:` the runtime class), its exact type, which declares `_replace(self, *, name: T0 = ..., ...)` and `_asdict() -> _dct_<fields>[...]` (a generic TypedDict, shown as `{name: str, ...}` in hover). basedpyright completes and checks field names, and check `**rec._asdict()` against the callee's parameters. They can't exist at runtime: NamedTuple refuses to let a class override them. The checkers' complaint about overriding final methods is silenced in the generated code. Measured: `if TYPE_CHECKING` must be spelled so pyright recognises it; `from typing import TYPE_CHECKING as _TC` isn't (pyright then reads both branches), `import typing as _t` + `_t.TYPE_CHECKING` is, and keeps `TYPE_CHECKING` out of the user's namespace. New public names like `replace`/`asdict` were rejected: they'd take names from fields and add API beyond binding by name. Output files don't get any of this.

- **`.pyn` tests through a pytest plugin, not a conftest:** the `pytest11` entry point makes it work in every project with byname installed (llm, cp), with no per-project file. It subclasses `pytest.Module` and overrides `_getobj` (pytest's own import path can't load `.pyn` with assert rewriting, which only hooks `.py`), building the module from `to_ast` so `rewrite_asserts` runs on the real tree. Measured: VS Code's Python extension discovery (`vscode_pytest`) reports `.pyn` files and their tests with the right `lineno`, so the gutter's run buttons appear. Its parametrized-test code splits the nodeid at `.py`, so a parametrized `.pyn` test gets an odd internal parent id (`…pynn::`); not tried in the editor. After adding the entry point, each project needs `uv sync --reinstall-package byname` for the metadata to register.

## Not yet built

**Designed, not built:**
- **Spreads in record types, `type Run = (**ModelConfig, **TrainConfig, seed: int)`**: every field of both, plus `seed`, for combining types without copying field lists (TS `ModelConfig & TrainConfig & { seed: number }`). A trailing `...` keeps it open as usual. Today `(**T, name: str)` is a syntax error ("a record built from spreads takes `**record` and `name=value` items"). Plan: expand the text before translating, `(**TrainConfig, name: str, ...)` → `(batch_size: int, lr: float, name: str, ...)`, so the checker only ever sees a plain record type and errors and hovers work unchanged. Limits: the alias must be a record-type `type` alias in the same file (an imported one is an error, not `Any`); a field in two parts is an error, not an override; aliases that spread aliases expand in order. Not for a function's own parameter type: `(**TrainConfig, ...)` there requires all of `TrainConfig`, same as `: TrainConfig`, which is why llm's `train`/`GPT` write their fields inline.
- **Function types, `encode: (s: str) -> list[int]`, `greet: (*, name: str, age: int) -> None`** (TS `(s: string) => number[]`). Today `(s: str)` parses as a record type and the `->` is a syntax error. `Callable[[str], list[int]]` works for positional parameters but drops their names (hover, keyword calls through a parameter). **Keyword-only functions, byname's usual style, can't be typed with `Callable` at all** (measured 2026-10-05): `def fn(*, name: str, age: int)` isn't assignable to `Callable[[str, int], None]`, and `Callable[..., None]` accepts it but checks nothing (`b(nme="x")` passed). The only way today is a hand-written Protocol, `class Greet(Protocol): def __call__(self, *, name: str, age: int) -> None: ...`, which checks calls (`c(name="rahul")` → missing `age`). Plan: `(params) -> T` is unambiguous (a record type is never followed by `->`) and would translate for the checker to exactly that Protocol, with the parameter list copied as written (`*`, defaults, `/`). Not built yet (2026-10-05): only needed where such a function is passed as a value or stored in a record field; first real use was a `type CharTokenizer = (vocab_size: int, encode: ..., decode: ...)` alias in llm's `src/records/second.pyn`. Tracked in open_issues.md.

**Ruled out along the way:**
- **Partial cast `cast((age: int, ...), r)`**, meaning "same record, `age` now `int`": needs an intersection type. Use a full `cast((name: str, age: int), r)`; it's checker-only, like TypeScript's `as`.
- **A generic merge, `a.merge(b)` or `def merge[A, B](a: A, b: B) -> A & B`**: the merged type of two unknown types is an intersection. Spreads (below) work instead because the target type is known where the record is used, or the result is `Any`.
- **Narrowing a record by a field:** `isinstance(r.age, int)` narrows `r.age`, not `r`, so `r._replace(age=99)` on a mixed union still fails. Keep record lists to one type, or annotate them (`rs: list[(name: str, age: int)] = [...]`).
- **`**` of a union of records:** with a mixed list, `fn(**rs[0]._asdict())` is flagged even when `fn` accepts both types, because basedpyright unpacks a union of TypedDicts as `object` values. Same remedy: one type per list.

**Smaller items:**
- Ctrl+click on a field inside a pattern. It goes nowhere now; the natural target is where the record was built.

## Conventions

- **Commits:** one-line subjects, no co-author trailer.
- **Python versions in the checker:** byname's own venv is 3.14, where annotations may name classes defined further down; users' projects (llm: 3.12) aren't. 21f1394 emitted each record's checker function before the `_typ_` Protocol it returns, so on 3.12 every record was `Unknown` and the undefined names were hidden as generated-code diagnostics. Fixed 2026-10-05 (types first); `test_records_are_typed_on_python_before_3_14` pins `pythonVersion` 3.12.
- **Tests:** `uv run pytest`. They're written to explain the behaviour, with real values in the asserts. `test_lsp.py`, `test_tools.py` and `test_fmt.py` drive the real basedpyright and Ruff, and skip if those aren't installed.
- **Extension changes:** bump `version` in `editors/vscode/package.json`, rebuild with `vsce package …`, then `code --install-extension byname.vsix --force` and Reload Window. Server-only changes just need Reload Window, since `.venv` is an editable install.
- **Measure before proposing:** several plausible mechanisms turned out false in practice, such as Ruff accepting call stand-ins.
